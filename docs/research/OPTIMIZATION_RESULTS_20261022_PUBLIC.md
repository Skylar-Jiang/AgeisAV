# AegisAV 准确率与扫描效率：2026-10-22

本轮默认扫描路径仅对 ≥1 MiB 文件并行执行模糊哈希与独立引擎，保留小文件原执行顺序。
不复用 Worker，不改变缓存、模型、阈值、规则和融合。候选原生哈希与模型均不进入生产。
Windows ClamAV 不可用，继续明确弃权；下列测速不能代表 ClamAV 健康运行的完整五引擎扫描。

## 瓶颈与工程改动

实际临时服务 profiling 覆盖认证上传、任务调度、进程启动、PE 校验、模糊哈希、ML 子进程、
报告 JSON 和 SQLite。YARA 构建约 1.1–1.3 秒，ClamAV 探测约 0.2 秒，SQLite 保存约 11–17 ms；
大文件纯 Python 模糊哈希约 10 秒，构成可与外置 ML 重叠的主要串行阶段。
ML 子进程的导入、PE 解析和特征提取仍明显占时。cProfile 会显著放大时间，仅用于归因，
不将带 profiler 的总耗时或各嵌套阶段相加作为提速依据。

此前全尺寸并行原型：9 个安装来源良性 PE、27 对受限进程扫描，P50 4.527→4.306 秒，
P95 22.438→14.178 秒，吞吐量 +37.1%；27 对报告除计时外一致。
小文件部分均值退化约 3.6%–4.8%，因此最终只对 ≥1 MiB 文件启用并行。
原型与最终源码不同，其整体收益不冒充最终源码的测量。

最终源码另行完成三轮、9 对真实认证 HTTP 任务，计时从客户端编码到任务终态响应，
包括上传、调度、Worker、报告与 SQLite；不与模型训练同时运行：

| 场景 | 基线 P50 / P95 | 最终源码 P50 / P95 |
|---|---:|---:|
| 小型 notepad | 3.218 / 3.225 秒 | 3.205 / 3.242 秒 |
| 6.6 MiB Python DLL | 16.021 / 17.188 秒 | 9.244 / 11.524 秒 |
| 4 输入混合批次（含 1 重复） | 10.454 / 10.495 秒 | 9.985 / 10.353 秒 |

大文件 P50 约下降 42.3%，混合批次约下降 4.5%。小文件基本持平，吞吐反而微降约 0.4%，
不宣称小文件提速。另一组小文件复验曾出现更大的尾延迟波动，原记录保留。
每场景仅三轮，P95 为该组三次最大值，不能据此给出稳定服务尾延迟保证。
9 对完整报告除计时外一致。两版本均实际观察运行中 Worker PID 后取消，
确认清理和下一任务成功；关闭服务后重开 SQLite，全部测量任务的持久化报告一致。

## 模型开发实验：明确淘汰

仅使用既有 480,000 行 FIT 和已经参与候选选择的 40,000 行开发验证特征。
最终测试向量、测试预测与原始恶意 PE 均未读取。验证集不是独立确认集。
比较对象是冻结的本地 Win64 **研究模型**；产品默认仍为通用模型，阈值 0.5。

候选同时减小叶数 64→32、增大最小叶样本 100→200、分箱 255→127、
分箱采样 200,000→20,000，保留 500 棵树及全部 2,568 维特征。它是复合探索，不能将变化归因于单一参数。

| 开发指标 | 冻结 Win64 研究基线 | 粗化候选 |
|---|---:|---:|
| FP=20 / 20,000 时 TP | 18,231 | 17,832 |
| 同预算 Recall | 91.155% | 89.160% |
| FP=100 时 TP | 19,162 | 19,058 |
| FP=200 时 TP | 19,552 | 19,459 |
| ROC-AUC | 0.998889 | 0.998665 |
| Average precision | 0.998938 | 0.998729 |
| 40,000 行推理 P50 | 2.695 秒 | 2.122 秒 |
| 模型大小 | 3,735,395 B | 1,952,189 B |

低 FPR 点少检出 399 个，四周 TP 差为 -112/-116/-67/-104。
样本级配对 Recall 差区间为 [-2.240, -1.750] 个百分点，未建模家族相关性和选择偏差。
推理约快 21.3%、模型约小 47.7%，不足以补偿检出退化，淘汰该候选。
推理计时为预载模型、固定 1,024 行分块、单线程、一次预热、五轮交替对照，
重复分数与保存预测完全一致；它不包括特征提取、启动和 HTTP。

两次全 FIT memmap 构建触发 1.5 GiB 主机余量保护并保存失败记录。
流式 NPY 读取完成构建 56.5 秒、训练 400.4 秒，采样 RSS 峰值约 1.90 GiB、private 约 3.21 GiB。
该次运行原生构建使用默认线程和 prefilter20，训练使用四线程/minleaf200；不能声称构建也受四线程限制。
精确源码快照、完整配置、模型和验证预测单独保留。
之后修正 Sequence 的参数传递：总种子、分箱种子、叶过滤和线程参数与 ndarray 构建一致。
小型直接/流式训练逐元素预测一致；未把修正后的加载器冒充已经重跑的全 FIT 候选。

5 个先前观察的 singlefilehost、SQLite、7-Zip 良性阳性控制再次复现完整特征摘要和通用模型分数。
既有 Win64 路由避开其中 4 个，粗化候选没有额外收益；Win32 7-Zip 仍告警。
这是按历史误报选择的开发控制，不能当独立 FPR 估计。没有白名单、恶意哈希回填或针对这些文件调阈值。
本轮没有 Emotet 新的原件实验或家族独立增益结论。

## 原生 SSDeep：有价值的研究候选

Apache-2.0 C 源码翻译当前固定 ppdeep 算法，保留署名和许可。
65 组输入包括空输入、低熵/随机边界、16 MiB 上限及安装来源良性 PE，哈希逐字相同；
四线程一致性和输入/输出预算拒绝通过。它不是上游 libfuzzy 的普遍兼容认证。
只在显式研究 Worker 中、进入既有 Windows Job 后校验 DLL 摘要并加载，生产不会自动选用。

4 个安装来源良性文件、三轮交替、12 对真实受限进程扫描：
P50 9.679→8.375 秒，P95 20.224→11.615 秒，吞吐量 0.0913→0.1280 文件/秒（+40.3%）；
采样 CPU 累计 142.64→80.38 秒（约 -43.7%）。
同时进程树 RSS 采样最大值 400.2→403.0 MiB，未见明显内存节约。
12 对报告仅三个耗时字段及明确标注的研究后端版本不同，哈希、分数、证据和裁决一致；全部清理确认。
该比较不含 HTTP，不能与其他文件集合的速度收益相乘。仍需扩大字节回归、ABI/便携打包和故障验收。
